# VoiceLinkVR 平台化升级方案（简化版）

> 基于 GPT 原始方案整理，用更简单直白的语言重新梳理，方便非技术人员理解。

---

## 一、我们现在有什么？（现状）

你可以把现在的系统想象成一个**小餐馆**：

| 模块 | 比喻 | 说明 |
|------|------|------|
| 语音识别/翻译 API | 厨房 | 核心能力，做"菜"的地方 |
| 用户登录 (JWT) | 门卡 | 用户拿用户名密码换一张"门卡"，之后刷卡进门 |
| 管理后台 (/ui) | 收银台 | 管理员管理用户、看统计 |
| 用户中心 + 爱发电 | 小卖部 | 用户充值、看余额、买套餐 |
| 请求日志/限流 | 监控摄像头 | 记录谁用了什么、用了多少 |

### 现在的数据库只有 4 张表

```
user           -- 一张表塞了所有东西：账号、密码、权限、套餐、余额、到期时间
account_token  -- 邮箱验证等临时令牌
request_log    -- 请求日志
payment_order  -- 爱发电订单
```

### 现在的登录方式

- **客户端**：用户名 + 密码 → 拿到 JWT token → 之后带着 token 调接口
- **管理后台**：用户名 + 密码 → Session 登录

就这两种，没有微信登录，没有邮箱登录，没有 OAuth2。

## 二、现在有什么问题？（为什么要改）

### 问题1：登录方式太原始

现在只能"用户名+密码"登录。想加微信登录、邮箱登录、官网网页登录，现有架构撑不住。

**打个比方**：现在的门卡系统只认一种钥匙。你想让用户用指纹、刷脸、手机NFC都能开门，就需要换一套门禁系统。

### 问题2：用户表太臃肿

一个 `user` 表同时存了：
- 你是谁（用户名、密码）
- 你有什么权限（管理员？）
- 你买了什么套餐（到期时间、额度、加油包）

就像一张身份证上同时写了你的银行余额和会员等级，以后改任何一个都很麻烦。

### 问题3：支付流程里带着密码

现在爱发电支付链接的生成依赖 `username + password`，`custom_id` 里有密码信息。这既不安全，也不适合"微信登录的用户想付款"这种场景。

### 问题4：没有官网

用户中心目前嵌在客户端里，没有独立的官网入口。

### 问题5：部署限制

- 家里的服务器有算力，但公网IP是动态的
- 公网服务器有固定IP，但性能弱
- 微信登录回调需要固定的公网地址

## 三、我们要做成什么样？（目标）

### 用户能感受到的变化

| 现在 | 以后 |
|------|------|
| 只能用户名密码登录 | 可以邮箱注册登录、微信扫码登录 |
| 用户中心在客户端里 | 用户中心在官网上，浏览器就能用 |
| 没有官网 | 有正式官网（产品介绍、下载、定价） |
| 充值要手动操作 | 官网上直接选套餐、付款、自动生效 |
| 只有一种登录方式 | 多种方式登录同一个账号 |

### 技术上的变化

| 现在 | 以后 |
|------|------|
| 简单 JWT 发放 | 标准 OAuth2 身份中心 |
| user 一张大表 | 身份、凭据、套餐、订单分开存 |
| 密码嵌入支付流程 | 支付基于登录态 + 订单号 |
| 所有服务在家里 | 公网服务器做入口，家里做计算 |

## 四、怎么改？（架构设计）

### 4.1 把系统拆成 5 个"区域"（逻辑上拆，代码还是一个项目）

```
+-------------------+     +-------------------+     +-------------------+
|   Identity 域     |     |    Portal 域      |     |   Billing 域      |
|   (身份认证)       |     |   (官网/用户中心)   |     |   (计费/支付)      |
|                   |     |                   |     |                   |
| - 邮箱注册/登录    |     | - 官网首页         |     | - 创建支付订单     |
| - 微信登录        |     | - 用户中心         |     | - 爱发电对接       |
| - OAuth2 授权     |     | - 套餐展示         |     | - 订单状态同步     |
| - 账号绑定        |     | - 用量查询         |     | - 套餐激活         |
+-------------------+     +-------------------+     +-------------------+

+-------------------+     +-------------------+
|   Compute 域      |     |    Admin 域       |
|   (语音/翻译)      |     |   (后台管理)       |
|                   |     |                   |
| - 语音识别        |     | - 用户管理         |
| - 翻译           |     | - 订单管理         |
| - TTS            |     | - 系统统计         |
| - 配额扣减        |     | - 手动补单         |
+-------------------+     +-------------------+
```

**重点**：这只是代码组织方式的变化，不是拆成5个独立服务。还是一个 FastAPI 项目，只是文件夹分得更清楚。

### 4.2 数据库怎么拆

**现在**：1张 user 表装所有东西

**以后**：按职责拆成多张表

```
身份相关：
  users              -- 主账号（id、昵称、状态、是否管理员）
  user_credentials   -- 登录凭据（密码、邮箱、是否验证）
  user_identities    -- 第三方身份（微信 openid 等）
  user_sessions      -- 登录会话

OAuth2 相关：
  oauth_clients           -- OAuth 应用（官网、客户端各算一个）
  oauth_authorization_codes -- 授权码（临时的，用完即弃）
  oauth_refresh_tokens     -- 刷新令牌

计费相关：
  subscriptions     -- 订阅记录（谁买了什么套餐、到期时间）
  addon_balances    -- 加油包余额
  plans             -- 套餐定义（月费、日额度等）

支付相关：
  payment_intents   -- 支付意图（谁要买什么、多少钱）
  payment_events    -- 支付事件（爱发电回调原始数据）
  entitlement_grants -- 权益发放记录（给谁发了什么）
```

### 4.3 部署方案

```
用户请求
  |
  v
[公网服务器] -- 固定IP、域名、HTTPS证书、反向代理
  |
  | (通过 FRP 隧道)
  v
[家里服务器] -- FastAPI主业务、数据库、Redis、Whisper、翻译服务
```

**简单说**：公网服务器只当"传话筒"，真正干活的还是家里的服务器。

### 4.4 域名规划

| 域名 | 用途 |
|------|------|
| `www.voicelinkvr.com` | 官网展示页 |
| `account.voicelinkvr.com` | 登录、注册、OAuth2、用户中心 |
| `api.voicelinkvr.com` | 客户端 API |
| `admin.voicelinkvr.com` | 后台管理 |

## 五、OAuth2 是什么？为什么需要它？

### 通俗解释

OAuth2 就是一套"授权标准"。你见过的"微信登录""QQ登录""GitHub登录"背后用的都是 OAuth2。

**没有 OAuth2 时**：每个应用都自己存用户名密码，各管各的。
**有了 OAuth2 后**：一个统一的"身份中心"管所有登录，各应用只需要找它要授权就行。

### 我们需要实现的 OAuth2 能力

| 能力 | 说明 | 优先级 |
|------|------|--------|
| Authorization Code + PKCE | 官网和客户端用这个方式登录 | 必须 |
| Refresh Token | 用户不用频繁重新登录 | 必须 |
| UserInfo 接口 | 获取当前登录用户信息 | 必须 |
| Token Revoke | 退出登录时让 token 失效 | 必须 |
| Client Credentials | 内部服务间调用 | 以后再说 |

### 新增的接口

```
认证接口：
  POST /auth/register/email     -- 邮箱注册
  POST /auth/login/password     -- 密码登录
  POST /auth/verify-email       -- 验证邮箱
  POST /auth/forgot-password    -- 忘记密码
  POST /auth/reset-password     -- 重置密码
  GET  /auth/wechat/start       -- 发起微信登录
  GET  /auth/wechat/callback    -- 微信登录回调
  POST /auth/logout             -- 退出登录

OAuth2 标准接口：
  GET  /oauth/authorize          -- 授权页面
  POST /oauth/token              -- 换取/刷新 token
  POST /oauth/revoke             -- 撤销 token
  GET  /oauth/userinfo           -- 获取用户信息
```

## 六、微信登录怎么做？

### 核心原则

微信登录不是一个独立的账号系统，而是一种"开门方式"。

就像你家的门可以用钥匙开，也可以用指纹开——不管怎么开，进去的都是同一个家。

### 登录流程（用户视角）

```
1. 用户在官网点击"微信登录"
2. 跳转到微信扫码页面
3. 用户扫码确认
4. 微信把用户信息给我们
5. 系统查找：这个微信号绑过我们的账号吗？
   |
   +-- 绑过 → 直接登录，进入用户中心
   |
   +-- 没绑过 → 引导用户：
       |
       +-- 已有账号 → 绑定现有账号
       +-- 新用户   → 创建新账号（需要补填邮箱）
```

### 账号绑定规则

- 一个微信只能绑一个账号
- 一个邮箱只能绑一个账号
- 一个账号可以同时有邮箱和微信两种登录方式

## 七、支付流程怎么改？

### 现在的问题

```
现在：用户名 + 密码 → 生成支付链接 → custom_id 里带密码 → 不安全
```

### 改造后

```
以后：用户已登录 → 选套餐 → 创建支付订单 → 生成支付链接 → 回调确认 → 自动发放权益
```

### 关键变化

| 对比项 | 现在 | 以后 |
|--------|------|------|
| 发起支付的前提 | 提供用户名+密码 | 用户已登录即可 |
| custom_id 内容 | 含密码信息 | 只含订单号+用户ID+签名 |
| 未注册用户 | 支付时自动开户 | 必须先注册再支付 |
| 订单追踪 | 靠 username 关联 | 靠 payment_intent_id 关联 |

## 十、风险提醒

| 风险 | 说明 | 应对 |
|------|------|------|
| 老用户迁移 | 现有用户数据要搬到新表里，可能出问题 | 写迁移脚本，先在测试库验证 |

- 一边做官网一边继续往旧 User 表上堆功能

# Claude 的评价

## 总体评价：方案方向正确，但对当前项目阶段来说过度设计

GPT 给出的方案在**架构分析**和**问题诊断**上是准确的，确实抓到了当前系统的核心痛点（登录原始、用户表臃肿、支付带密码、缺乏官网）。但在**解决方案的复杂度**上，明显超出了当前项目的实际需要。

## 具体评价

### 做得好的部分

1. **问题诊断准确**：GPT 准确指出了 `custom_id` 带密码、user 表过于扁平、缺乏 OAuth2 等核心问题，这些确实需要解决。

2. **部署方案务实**："公网轻入口 + 家里主业务" 的 FRP 方案非常贴合你的实际环境，这是正确的思路。

3. **分阶段推进合理**：先做数据模型、再做身份中心、最后做官网页面的顺序是对的，避免了"先搭花架子后面全返工"的陷阱。

4. **兼容性考虑周到**：保留旧 `/api/login` 接口、旧订单兼容处理等，说明考虑到了线上已有用户的平滑过渡。

### 过度设计的部分

1. **OAuth2 全套实现没有必要**

   你的场景是：官网 + 一个客户端 + 一个管理后台。这三个都是你自己的应用，不是第三方。对于这种场景，完整的 OAuth2 Authorization Code + PKCE 流程是**大炮打蚊子**。

   **我的建议**：先用简化方案——统一的 JWT 签发中心 + Refresh Token 就够了。等真正需要接入第三方应用时再上完整 OAuth2。

2. **数据库表拆得太碎**

   GPT 方案建议拆出 13+ 张新表（users, user_credentials, user_identities, user_sessions, oauth_clients, oauth_authorization_codes, oauth_refresh_tokens, subscriptions, addon_balances, plans, payment_intents, payment_events, entitlement_grants）。对于当前用户规模，这个拆分粒度过细。

   **我的建议**：
   - `user` 表拆成 `users` + `user_credentials` + `user_identities` 就够了
   - 套餐和加油包暂时留在 users 表里，等业务真正复杂了再拆
   - 支付相关用 `payment_intents` 替代当前 `payment_order` 即可，不需要单独的 `payment_events` 和 `entitlement_grants`

3. **5 个逻辑域划分过早**

   当前项目只有一个开发者（你），代码量也不大。把代码分成 Identity/Portal/Billing/Compute/Admin 五个域，增加了认知负担但没有带来实际收益。

   **我的建议**：保持现有的 `routers/` 目录结构，新增 `auth.py`（认证）和 `portal.py`（官网/用户中心）两个路由文件就够了。

4. **域名规划过于理想化**

   4 个子域名意味着 4 套证书、4 条 FRP 隧道配置、更复杂的反向代理规则。

   **我的建议**：用路径区分而非子域名。例如 `voicelinkvr.com/auth/*`、`voicelinkvr.com/portal/*`、`voicelinkvr.com/api/*`。一个域名、一套证书、一条隧道，简单得多。

### 遗漏的部分

1. **没有评估工作量**：7 个阶段说起来轻松，但对于单人开发，这是一个非常庞大的工程。GPT 没有帮你评估每个阶段需要多少工作，也没有建议哪些可以砍掉。

2. **没有考虑现有代码的迁移成本**：项目里还保留着完整的旧 Flask 代码（`src/server.py`，1600+ 行），GPT 方案完全没提这个文件该怎么处理。

3. **没有给出具体的技术选型**：比如 OAuth2 用什么库实现？用 `authlib` 还是自己写？邮件服务用什么？这些实操层面的决策一个都没给。

## 我的替代建议：分 3 步走的精简方案

如果让我来设计，我会把 7 个阶段压缩成 3 步：

### 第1步：身份系统升级 + 支付脱敏

- `user` 表新增 `email`/`email_verified` 字段（已有）
- 新增 `user_identities` 表（存微信 openid）
- 支付流程去掉密码，`custom_id` 只放订单ID + 签名
- 新增 `/auth/*` 路由：邮箱注册、邮箱登录、微信登录
- 保留旧 `/api/login` 兼容

### 第2步：官网 + 用户中心

- 用 FastAPI + Jinja2 模板做官网（和现有管理后台一样的技术栈）
- 用户中心页面：账户、用量、套餐、订单、绑定
- 官网静态页：首页、介绍、定价、下载

### 第3步：公网部署

- 公网服务器配置 Nginx + FRP
- 一个域名，路径区分功能
- 配置微信回调地址
- 灰度上线

**这个方案做的事情一样，但复杂度大约是 GPT 方案的 1/3。**

## 一句话总结

> GPT 方案是一份合格的"架构师级别"的技术蓝图，适合10人团队参考；但对于当前1人开发的项目，需要大幅精简后再落地执行。先解决最痛的问题（支付带密码、缺少微信/邮箱登录），其余的等业务真正需要时再补。
