# V2 请求日志重构方案

## 1. 背景

当前这套“请求日志表兼做业务事实表”的设计，至少会让日志结构同时承担以下任务：

- 请求审计与排障
- 配额扣减结果落库
- 用户历史用量查询
- 后台统计报表

当前线上数据库使用 MariaDB。需要特别说明的是：

- 当前 V2 里的 `v2_request_log` 还是空表
- 约 3000 万行的历史规模，来自更老一代后端的 `request_log` 日志库

这组历史数据说明旧结构一旦长期积累，会带来非常高的迁移和维护成本。现有设计带来的主要问题有：

- 单表过大，迁移、导出、导入都很慢
- 明细日志表被当成业务真相表使用
- 用户用量和后台统计都直接扫明细表
- 历史数据无法轻松清理，因为清理会影响配额和报表
- 启动升级逻辑中存在对日志大表全表扫描的风险

本方案的目标不是简单把一张大表换成另一张大表，而是把在线业务从“大表依赖”中解耦出来。

### 1.1 当前项目的额外前提

结合当前仓库和线上现状，还需要补充一个非常关键的事实：

- `v2_request_log` 目前仍然是空表
- 约 3000 万行的历史请求明细来自老后端的 `request_log` 日志数据库
- 这批历史数据应视为“老系统历史日志源”，而不是“当前 V2 在线热表”
- 因此本次重构不需要承担“保留 v2 旧日志兼容写法”的历史包袱

这意味着：

- V2 新结构可以一步到位切换
- 不一定需要经历长期双写阶段
- 老后端 `request_log` 可以直接被视为“历史归档来源”而不是“V2 新结构必须兼容的在线表”

### 1.2 当前方案的默认决策

基于目前信息，本方案默认采用以下决策：

- 不迁移老后端 `request_log`
- 不回填老日志到 V2 新结构
- 不把老日志重塑成新的统计表或事件表
- V2 直接从新结构开始积累数据

老后端日志的处理方式调整为：

- 原样留档
- 按需离线查询
- 不进入 V2 在线读写路径

## 2. 当前结构的核心问题

### 2.1 单表职责过多

当前 `v2_request_log` 同时承担：

1. 请求明细日志
2. 配额扣减流水
3. 用户用量查询数据源
4. 后台统计数据源

这会导致一个问题：只要日志表变慢，整条业务链都会一起变慢。

### 2.2 日志表不应作为配额真相来源

日志天然适合做：

- 审计
- 观察
- 排障

日志天然不适合长期直接做：

- 额度真相
- 日统计真相
- 热路径实时查询

因为日志需要保留、归档、压缩、清理，而配额真相需要稳定、精确、可快速查询。

### 2.3 迁移成本过高

当前若要迁移或重构：

- 需要导出大量 SQL 文本
- 再重新解析并导入
- 导入时还要维护多列索引
- 旧表很大，数据转移窗口长

这也是当前“数据转移很慢”的根本原因之一。

### 2.4 冷热数据没有分层

当前所有数据都被当成“热数据”对待。实际上：

- 最近 1 到 30 天的审计日志才可能需要快速查明细
- 历史 30 天以上的请求明细大多只用于偶发追溯
- 用户配额和报表只需要聚合结果，不需要持续依赖历史明细

---

## 3. 设计目标

本次重构目标如下：

1. 不再让 `v2_request_log` 承担核心业务真相职责
2. 把配额查询从明细日志表中拆出来
3. 把后台统计从明细日志表中拆出来
4. 保留必要的历史审计能力
5. 让历史明细可以独立归档和清理
6. 让后续迁移和扩容不再依赖 3000 万行大表

---

## 4. 推荐方案总览

推荐采用“四层结构”：

1. `v2_request_audit_log`
2. `v2_usage_event`
3. `v2_subject_daily_usage`
4. `v2_endpoint_hourly_stats`

其中：

- `v2_request_audit_log` 是冷大表，只做审计与排障
- `v2_usage_event` 是业务事件表，只记录真正和额度有关的请求
- `v2_subject_daily_usage` 是用户或 IP 的按日真相表
- `v2_endpoint_hourly_stats` 是后台图表和排行表

核心原则：

- 配额问小表
- 报表问小表
- 审计才问大表

---

## 5. 是否保留大表

### 5.1 推荐结论

推荐保留“冷大表”，不推荐继续保留“热大表依赖”。

换句话说：

- 推荐有冷大表
- 不推荐有热大表

### 5.2 为什么推荐冷大表

相比“完全无大表”，保留冷大表有这些优势：

- 保留完整审计能力
- 可以追查投诉、限流、误扣费、异常请求
- 支持支付、风控、管理员排障时的历史定位
- 对迁移更友好，不需要立刻放弃所有旧明细

### 5.3 冷大表的限制

冷大表必须满足以下条件：

- 不参与配额计算
- 不参与后台统计
- 不参与用户实时查询
- 不参与启动升级逻辑
- 必须有明确保留期
- 必须允许归档或按分区删除

---

## 6. 新表职责设计

## 6.1 `v2_request_audit_log`

用途：

- 审计
- 排障
- 关联 `request_id`
- 查询某次请求的上下文

建议字段：

- `id`
- `request_id`
- `created_at_utc`
- `user_uuid`
- `username`
- `actor_type`
- `ip`
- `host`
- `method`
- `endpoint`
- `status`
- `status_code`
- `duration_ms`
- `quota_scope`
- `quota_source`
- `resource_cost`
- `resource_deducted`
- `error_code`
- `extra_payload`

说明：

- 这张表是冷表，不作为额度真相来源
- 建议按月分区
- 建议只保留最近 30 到 180 天

## 6.2 `v2_usage_event`

用途：

- 记录真正影响配额或业务判断的事件
- 为特殊追查提供较高价值明细

建议只记录以下请求：

- `resource_deducted = true`
- `status = rate_limited`
- `status >= 500`
- 认证、计费、管理员关键操作

建议字段：

- `id`
- `event_time_utc`
- `request_id`
- `subject_type`
- `subject_key`
- `user_uuid`
- `username`
- `endpoint`
- `status`
- `quota_source`
- `resource_cost`
- `resource_deducted`
- `extra_payload`

说明：

- 这张表比审计表更偏业务事件
- 规模会明显小于全量请求日志
- 可保留更久，比如 180 到 365 天

## 6.3 `v2_subject_daily_usage`

用途：

- 用户或测试 IP 的按日额度真相
- 用户最近 N 天用量查询
- 当天已用额度和剩余额度查询

建议一条记录代表：

- 某个用户在某一天
- 或某个 IP 在某一天

建议字段：

- `usage_date`
- `subject_type`
- `subject_key`
- `user_uuid`
- `username`
- `success_count`
- `failed_count`
- `rate_limited_count`
- `total_count`
- `daily_resource_used`
- `addon_resource_used`
- `deducted_request_count`
- `last_request_at`

主键建议：

- `(usage_date, subject_type, subject_key)`

说明：

- 这是新的“每日用量真相表”
- 配额查询直接查这张表
- 不再需要从大日志表实时聚合

## 6.4 `v2_endpoint_hourly_stats`

用途：

- 后台统计图表
- Top endpoint
- 按小时成功率、失败率、限流率

建议字段：

- `stat_hour_utc`
- `endpoint`
- `method`
- `success_count`
- `failed_count`
- `rate_limited_count`
- `total_count`
- `resource_cost_sum`
- `duration_sum_ms`
- `p95_duration_ms`

说明：

- 这张表只服务后台
- 数据量会远小于原始日志表
- 后台统计不再需要扫明细

## 7. 推荐数据流

### 7.1 写入流程

请求结束后：

1. 判断是否扣减资源
2. 若扣减资源，则更新 `v2_subject_daily_usage`
3. 若为高价值事件，则写入 `v2_usage_event`
4. 若为审计需要，则写入 `v2_request_audit_log`
5. 异步或定时更新 `v2_endpoint_hourly_stats`

### 7.2 查询流程

用户配额查询：

- 直接查 `v2_subject_daily_usage`

用户最近 7 天用量：

- 直接查 `v2_subject_daily_usage`

后台统计面板：

- 直接查 `v2_endpoint_hourly_stats`

问题排查：

- 查 `v2_request_audit_log`

关键业务追溯：

- 查 `v2_usage_event`

---

## 8. 为什么新结构比旧结构更合理

### 8.1 热路径不再依赖大表

旧结构下：

- 一个用户查 7 天用量，可能扫描大量请求明细

新结构下：

- 一个用户查 7 天用量，理论上只需要查 7 行

### 8.2 审计和业务真相分离

旧结构下：

- 日志删不了，因为删了可能影响额度统计

新结构下：

- 审计日志可以清理
- 额度真相不受影响

### 8.3 迁移难度显著下降

旧结构下：

- 每次重构都要考虑如何搬整张大日志表

新结构下：

- 只需要回填最近 30 到 90 天的小表
- 冷大表可以慢慢归档

### 8.4 后台统计更稳定

旧结构下：

- 后台图表和排行依赖大表聚合

新结构下：

- 后台直接读小时聚合表

### 8.5 未来扩展更容易

例如后续如果增加：

- 新的配额类型
- 新的审计字段
- 新的后台图表

不会再挤到同一张大日志表里。

## 9. MariaDB 下的存储与保留建议

## 9.1 冷大表建议按月分区

适用表：

- `v2_request_audit_log`
- `v2_usage_event`

建议：

- 按月分区
- 每月新增未来分区
- 定期删除过期分区

这样做的优势：

- 清理历史数据更快
- 归档边界清晰
- 查询最近时间范围时更容易裁剪分区

## 9.2 保留周期建议

建议默认保留策略：

- `v2_request_audit_log`：30 到 90 天
- `v2_usage_event`：180 到 365 天
- `v2_subject_daily_usage`：2 年以上
- `v2_endpoint_hourly_stats`：2 年以上

---

## 10. 为什么 SQL 导出再导入会慢

当前采用 MariaDB 导出 SQL，再执行 SQL 导入，这种方式通常较慢，原因包括：

- 每一行都被转成文本 SQL
- 导入时数据库要重新解析 SQL
- 导入过程中需要不断维护索引
- 文本文件体积大，I/O 开销高
- 大表场景下耗时会明显放大

因此在本次重构中，不推荐把“SQL dump/import”作为主迁移方案。

更推荐以下方式：

### 10.1 库内分批迁移

适用场景：

- 同库新旧表重构

推荐方式：

- `INSERT INTO new_table (...) SELECT ... FROM old_table WHERE ...`
- 按时间范围分批
- 按主键范围分批

### 10.2 并行逻辑迁移

适用场景：

- 跨实例迁移
- 无法使用物理备份恢复

推荐工具：

- `mydumper`
- `myloader`

### 10.3 物理备份恢复

适用场景：

- 整库迁移
- 全实例搬迁

推荐工具：

- `mariadb-backup`

## 11. 为什么默认不做迁移

对于当前项目，默认不建议把老后端 `request_log` 迁移到 V2 新结构，原因如下：

### 11.1 历史数据来源不是当前 V2

这 3000 万行数据来自更老一代后端，而不是当前 V2 运行过程中自然积累出来的数据。

这意味着：

- 字段口径可能不同
- 路由命名可能不同
- 认证方式和用户标识可能不同
- 配额和统计语义可能不同

即使技术上可以迁移，业务上也未必值得作为当前 V2 的在线基线。

### 11.2 迁移收益很有限

当前 V2 的 `v2_request_log` 还是空表，V2 完全可以从新结构开始积累数据。

在这种前提下，迁移老日志的主要收益通常只剩：

- 历史看起来更完整
- 图表时间跨度更长

但这些收益通常不足以覆盖迁移成本。

### 11.3 迁移成本明显偏高

如果要迁移老日志，就必须额外处理：

- 老日志到新结构的字段映射
- 老接口到新 endpoint 口径的映射
- 老用户标识到新 `subject_key` 的映射
- 老状态值到新统计口径的映射

同时还要承担：

- 导出导入时间
- 批处理脚本维护
- 历史数据质量校验
- 统计偏差解释成本

### 11.4 更合理的策略是“历史留档，未来纠正”

对于当前项目，更合理的做法不是重塑历史，而是：

- 老日志留档
- 新系统从正确结构开始
- 今后的在线统计全部基于新结构

这会让方案更便宜、更干净，也更容易长期维护。

## 12. 不迁移情况下的实施策略

推荐分阶段实施，但默认不做任何历史迁移。

## 阶段 0：立即止损

必须先做：

1. 移除启动阶段对 `request_log` / `v2_request_log` 的全表扫描
2. 停止把日志表当额度真相来源
3. 统一日志时间写入为 UTC

说明：

- 启动阶段不允许再全表 `.all()`
- 大日志表的历史补丁逻辑应迁移到离线脚本

## 阶段 1：上线新表

新增：

- `v2_subject_daily_usage`
- `v2_endpoint_hourly_stats`
- `v2_usage_event`
- `v2_request_audit_log`

## 阶段 2：V2 直接切换

由于 `v2_request_log` 为空表，建议直接这样做：

- V2 请求不再写入 `v2_request_log`
- V2 请求直接写入新结构
- V2 配额查询直接读取 `v2_subject_daily_usage`
- V2 后台统计直接读取 `v2_endpoint_hourly_stats`

这种方式的优势是：

- 不需要维护旧 V2 明细结构
- 不需要做 V2 明细双写核对
- 代码路径更简单
- 数据模型可以直接按最终形态落地

如需降低切换风险，可以保留极短的观察窗口，例如：

- 1 到 2 天灰度观察

但不建议再做长期双写。

## 阶段 3：不做历史回填

当前默认建议为：

- 不从老后端 `request_log` 回填任何数据
- 不把老日志导入 `v2_subject_daily_usage`
- 不把老日志导入 `v2_endpoint_hourly_stats`
- 不把老日志导入 `v2_usage_event`
- 不把老日志导入 `v2_request_audit_log`

这样做的好处是：

- 方案最简单
- 口径最干净
- 没有历史污染
- 没有迁移窗口
- 没有重塑脚本维护成本

## 阶段 4：切换读路径

由于 V2 明细表本身为空，这一步可以和阶段 2 合并上线：

1. 配额查询切到 `v2_subject_daily_usage`
2. 用户用量接口切到 `v2_subject_daily_usage`
3. 后台图表切到 `v2_endpoint_hourly_stats`
4. 审计查询切到 `v2_request_audit_log`

## 阶段 5：旧表降级

当前更应该处理的是老后端 `request_log` 历史日志的归档边界，而不是空的 `v2_request_log`。

建议做法：

- 保留老后端 `request_log` 作为 `legacy_request_log_archive`
- 或迁移到单独归档库
- 或导出为离线归档数据

旧表只读保留，不再参与：

- V2 配额
- V2 用户用量查询
- V2 后台统计
- 启动升级逻辑

## 阶段 6：归档与清理

最后做：

- 冷表分区
- 冷表归档
- 老后端 `request_log` 原样留档
- 删除过期分区

## 12.1 当前项目的最优落地路线

如果完全基于当前实际情况，我更推荐这条“短路径”：

1. 删除或下线所有对日志大表的启动期全表扫描
2. 新建 `v2_subject_daily_usage`
3. 新建 `v2_endpoint_hourly_stats`
4. 新建 `v2_usage_event`
5. 新建 `v2_request_audit_log`
6. 直接修改 V2 中间件写入逻辑，停止写 `v2_request_log`
7. 直接修改 V2 配额读取逻辑，改读 `v2_subject_daily_usage`
8. 直接修改 V2 后台统计逻辑，改读 `v2_endpoint_hourly_stats`
9. 老后端 `request_log` 只做留档，不做回填
10. 新系统从新结构开始独立积累数据

这条路线的核心优势是：

- 不和空的 `v2_request_log` 做兼容纠缠
- 不做长期双写
- 不做任何历史迁移
- 直接把 V2 带到最终结构

对当前项目来说，这是比“先兼容、再双写、再切换”更便宜也更干净的做法。

---

## 13. 推荐落地优先级

如果只做最小但高收益改动，建议优先级如下：

1. 去掉启动时对日志大表的全表扫描
2. 新增 `v2_subject_daily_usage`，把配额和用户日用量从大表里拆出去
3. 新增 `v2_endpoint_hourly_stats`，把后台统计从大表里拆出去
4. 直接放弃 `v2_request_log` 作为 V2 的目标明细表
5. 最后再做分区和历史留档

---

## 14. 最终推荐

针对当前项目，最终推荐方案是：

- 保留冷大表
- 放弃热大表依赖
- 用小表承载配额与报表真相

最终结构建议为：

- `v2_request_audit_log`
- `v2_usage_event`
- `v2_subject_daily_usage`
- `v2_endpoint_hourly_stats`

不再推荐继续让：

- `v2_request_log`

同时承担：

- 审计
- 配额
- 用户用量
- 后台统计

这正是旧结构在历史规模达到 3000 万行后会逐渐变慢、迁移困难、维护成本升高的根本原因。

结合当前实际情况，还可以进一步明确：

- 由于 `v2_request_log` 当前为空，V2 可以直接放弃它
- 真正需要处理的大历史数据源是老后端 `request_log`
- 因此本次最优方案是“V2 一步到位换新结构，老日志单独留档，不做迁移”

---

## 15. 一句话总结

本方案的核心不是“消灭所有大表”，而是：

**让大表退出核心业务路径，让小表承担在线真相。**

这样即使历史审计明细继续增长，也不会再拖累额度计算、用户查询、后台统计和后续迁移。

在当前项目里，这句话还可以进一步具体化为：

**老日志不迁移，V2 直接用新结构开始。**
