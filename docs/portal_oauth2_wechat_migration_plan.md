# 官网 / 认证中心 / 用户中心改造方案

## 文档说明

- 本文档基于当前仓库已提交版本的后端结构整理，不包含工作区中未提交改动。
- 目标是为以下事项提供统一改造方案：
  - 官网建设
  - 统一认证中心
  - 将用户中心与爱发电相关功能从客户端迁移到官网
  - 支持邮箱注册与登录
  - 在“家庭动态公网 IP + 公网服务器 FRP 稳定入口”的部署约束下设计可落地方案
- 本文档是架构与实施计划，不包含本地验证与测试执行。

### 当前范围确认

- 当前版本不做微信登录。
- 原因是当前账号条件不支持把微信登录做成稳定、正式、低维护成本的官网登录方案。
- 微信相关设计保留为未来备选方案，不纳入当前实施范围。
- 当前版本不做完整 OAuth2。
- 原因是当前客户端与官网均为自研、自控，没有第三方接入和标准授权平台的迫切需求。
- 当前版本采用“统一认证中心”方案：
  - 官网使用 Web Session
  - 客户端使用 Access Token + Refresh Token
  - 所有系统统一收敛到内部 `user_id`

## 1. 当前后端结构总结

当前项目已经不是单纯的语音 API，而是一个单体 FastAPI 业务后端，主要包含以下能力：

- 语音识别与翻译 API
- 用户登录与 JWT 鉴权
- 用户中心与爱发电支付激活
- 管理 API
- Web 管理后台
- 请求日志、限流、额度扣减
- 定时任务

### 1.1 主应用入口

主入口位于 `src/main.py`，当前负责：

- 应用启动与关闭
- 自动建表与数据库字段补丁
- 过滤配置加载
- 语言初始化
- 请求日志中间件
- 限流与额度提交
- 路由挂载
- 定时任务注册

当前挂载的主要路由组：

- `/ui` 管理后台页面
- `/api` 客户端 API
- `/api/user-center` 用户中心与爱发电
- `/manageapi` 管理 API

### 1.2 路由分层

#### `/api`

主要承担客户端能力接口：

- 登录
- 账户状态
- 用量统计
- 音频转写
- 音频翻译
- 文本翻译
- TTS

这部分本质上是“资源服务 API”。

#### `/api/user-center`

主要承担用户中心和爱发电逻辑：

- 支付指引
- 生成支付链接
- 手动激活订单
- Webhook 自动激活

这部分已经具备独立业务域雏形，但与现有账号体系耦合较深。

#### `/manageapi`

主要承担管理员接口：

- 创建管理员
- 创建用户
- 更新用户
- 删除用户
- 修改密码

#### `/ui`

当前是传统管理后台，支持：

- 管理员登录
- 用户列表与详情
- 爱发电订单管理
- 统计页

### 1.3 当前鉴权模型

目前系统存在两套身份体系并存：

#### JWT API 鉴权

- 用户通过 `/api/login` 提交用户名密码
- 服务端返回 JWT
- 之后 API 通过 Bearer Token 访问

这是“登录发 token”的模式，不是完整 OAuth2 授权中心。

#### Session 后台鉴权

- `/ui/login` 走 session 登录
- 后台通过 `SessionMiddleware` 维护管理员会话

### 1.4 当前数据模型

核心表只有三张：

#### `user`

当前同时承载：

- 账号身份
- 密码
- 管理权限
- 套餐额度
- 到期时间
- 加油包余额

#### `request_log`

记录：

- 用户名
- IP
- 接口
- 请求耗时
- 请求状态
- 资源消耗
- 资源来源

#### `payment_order`

记录：

- 爱发电订单号
- 商户订单号
- custom_id
- 用户名
- 操作类型
- 金额
- 激活结果
- 激活来源

### 1.5 当前业务特点

当前系统有以下几个重要特点：

- 配额逻辑已经比较复杂，支持订阅日额度与加油包额度
- 爱发电支付已经不是简单“回调记账”，而是会直接触发套餐/资源发放
- 请求日志与资源扣减已经形成完整链路
- 旧客户端兼容逻辑仍然存在
- 仓库中仍保留旧 Flask 服务代码，属于历史遗留

## 2. 当前结构存在的主要问题

### 2.1 当前不是统一认证中心

现有登录模式仅适合旧客户端直接调用 API，不足以支持：

- 官网网页登录
- 多终端统一会话与刷新
- 邮箱注册、找回密码、站内会话管理

### 2.2 用户模型过于扁平

当前 `user` 同时承担：

- 主账号
- 密码凭据
- 订阅状态
- 加油包资产
- 权限

这会导致后续扩展以下能力时变得困难：

- 邮箱注册/验证
- 微信身份绑定
- 一个账号多种登录方式
- OAuth2 client / session / token 管理

### 2.3 爱发电支付逻辑和旧账号模式耦合过深

当前爱发电流程里，支付指引和支付链接生成仍依赖：

- `username`
- `password`

并且 `custom_id` 里仍携带密码语义。这种模型不适合：

- 官网已登录用户发起支付
- 微信登录用户购买
- 邮箱注册用户购买
- 账号绑定与合并

### 2.4 官网、后台、资源 API 尚未做明确边界隔离

当前所有核心业务都在一个单体后端中，但边界还没有真正抽清楚：

- 管理后台和用户中心不是同一种权限域
- OAuth2 与 API 鉴权未统一
- 官网未来会和后台共享部分数据，但不应共享鉴权方式

### 2.5 当前数据库演进方式不适合后续阶段

当前数据库升级逻辑主要依赖：

- 启动时检测字段
- 缺字段即 `ALTER TABLE`

这适合快速演进，不适合进入“身份中心 + 支付资产 + OAuth2”的阶段。

### 2.6 部署环境存在公网入口与算力分离问题

当前现实约束是：

- 家里服务器有主算力和主要服务
- 家庭公网 IP 是动态的
- 微信/公众号/支付回调需要稳定公网入口
- 公网服务器有静态 IP，但性能较弱
- 不希望把计算服务、数据库或大型新容器迁移到公网服务器

因此后续方案必须把“稳定入口”和“主业务/主算力”分离。

## 3. 改造目标

本轮改造的最终目标应定义为：

### 3.1 用户侧目标

- 建立正式官网
- 将用户中心迁移到官网
- 将爱发电购买、激活、订单查询迁移到官网
- 支持邮箱注册、邮箱登录、找回密码、邮箱验证
- 支持账号绑定与合并

### 3.2 平台侧目标

- 建立统一认证中心
- 统一官网与客户端登录状态
- 将语音/翻译 API 转化为统一鉴权保护的资源服务
- 为未来升级到 OAuth2 / OIDC 预留结构空间

### 3.3 部署侧目标

- 公网服务器只承担稳定入口职责
- 家庭主机继续承担主要业务与计算
- 不把 Whisper / SenseVoice / 翻译 / 数据库迁到公网服务器
- 微信、公众号、支付回调仍具备稳定可用的公网域名与 HTTPS

建议后续按“逻辑域”重构，而不是一开始就强拆成多个物理微服务。

### 4.1 推荐逻辑分层

#### 1. Identity 身份与认证域

负责：

- 邮箱注册

- 邮箱验证
- 密码找回
- 微信登录

#### 2. Portal 官网与用户中心域

负责：

- 用量查询
- 套餐展示
- 订单页
- 账号绑定页
- 下载页与文档页

#### 3. Billing 计费与爱发电域

负责：

- 支付意图创建
- 爱发电支付链接生成
- Webhook 回调
- 订单状态同步
- 套餐激活
- 加油包发放

#### 4. Compute 语音与翻译资源域

负责：

- 语音识别
- 音频翻译
- 文本翻译
- TTS

负责：

- 用户管理
- 订单管理

- 公网服务器仅提供域名入口、HTTPS、反向代理、FRP 服务端

## 5. 当前版本认证中心设计建议

### 5.1 设计原则

不要继续沿用“只有 `/api/login` 返回 JWT”的模型，而应建设正式认证中心。

当前版本建议最小实现：

- 邮箱注册
- 邮箱登录
- 找回密码
- Web Session
- Refresh Token
- Token 撤销 / 退出登录

### 5.2 推荐接口

建议新增：

- `/auth/register/email`
- `/auth/login/password`
- `/auth/verify-email`
- `/auth/forgot-password`
- `/auth/reset-password`
- `/auth/wechat/start`
- `/auth/wechat/callback`
- `/auth/logout`

### 5.3 当前版本不做完整 OAuth2

当前版本不建议实现：

- `/oauth/authorize`
- `/oauth/token`
- `/oauth/clients`
- PKCE
- 第三方 consent 流程

原因：

- 当前官网与客户端均为自研
- 暂无第三方应用授权需求
- 当前核心问题是统一认证与会话管理，不是标准授权平台

未来如需开放平台、插件市场、第三方接入，再升级到完整 OAuth2 / OIDC。

### 5.4 旧接口兼容策略

现有 `/api/login` 不应立即删除。

建议分三步：

1. 保留旧 JWT 登录接口
2. 新客户端与官网统一迁移到新认证中心
3. 旧客户端完成迁移后，再逐步废弃 `/api/login`

## 6. 用户与身份模型重构建议

### 6.1 不建议继续只用 `user` 一张表

建议最少拆成以下模型：

#### `users`

保存主账号实体：

- `id`
- `display_name`
- `status`
- `is_admin`
- `created_at`
- `updated_at`

#### `user_credentials`

保存账号凭据：

- `user_id`
- `credential_type`
- `password_hash`
- `email`
- `email_verified_at`

#### `user_identities`

保存第三方身份：

- `user_id`
- `provider`
- `provider_app_id`
- `openid`
- `unionid`
- `provider_user_info`

#### `user_sessions`

保存 Web 登录态：

- `session_id`
- `user_id`
- `ip`
- `user_agent`
- `expires_at`

#### `oauth_clients`

保存 OAuth 客户端：

- `client_id`
- `client_name`
- `redirect_uris`
- `client_type`
- `scopes`

#### `oauth_authorization_codes`

保存授权码：

- `code`
- `user_id`
- `client_id`
- `redirect_uri`
- `expires_at`
- `code_challenge`

#### `oauth_refresh_tokens`

保存刷新令牌：

- `token_id`
- `user_id`
- `client_id`
- `scopes`
- `expires_at`
- `revoked_at`

### 6.2 套餐与账号资产模型建议

建议把订阅权益从用户主表里逐步拆出：

#### `subscriptions`

- `user_id`
- `plan_id`
- `status`
- `starts_at`
- `expires_at`

#### `addon_balances`

- `user_id`
- `resource_balance`
- `resource_total`
- `expires_at`

#### `plans`

- `plan_code`
- `monthly_price`
- `daily_quota`
- `display_name`

这样做之后：

- 用户模型更干净
- 支付发放权益更清晰
- 账号合并与迁移更容易

## 7. 微信公众号登录设计

> 本章节保留为未来备选设计，当前版本不实施微信登录。

### 7.1 总体原则

微信公众号登录不要设计成独立账号体系，而要作为“身份绑定方式”。

内部唯一主身份应该始终是：

- `user_id`

微信只是该用户的一种登录身份。

### 7.2 建议的登录流程

1. 用户在官网点击“微信登录”
2. 浏览器跳转到微信网页授权
3. 微信回调到 `account.example.com`
4. 身份中心不直接访问微信接口，而是调用部署在公网服务器上的 `wechat-connector`
5. `wechat-connector` 使用公网服务器固定公网 IP 请求微信接口并换取微信身份信息
6. 根据 `openid/unionid` 查找已绑定账号
7. 已绑定则直接登录
8. 未绑定则进入绑定流程：
   - 绑定现有账号
   - 或创建新账号并补充邮箱

### 7.3 标识选择建议

优先级建议如下：

- 优先使用 `unionid`
- 无 `unionid` 时，用 `appid + openid`

不要只把微信昵称或头像当作账号依据。

### 7.4 账号绑定原则

建议支持：

- 微信绑定已有邮箱账号
- 邮箱账号绑定微信
- 同一用户多种登录方式并存

不建议允许：

- 同一个微信身份绑定多个内部账号
- 同一个邮箱身份绑定多个内部账号

### 7.5 微信 IP 白名单处理原则

微信公众号相关服务端接口通常受“开发者 IP 白名单”限制。

这里需要明确：

- FRP 主要解决公网入站访问
- 微信 IP 白名单限制的是服务端访问微信接口时的“出站公网 IP”
- 因此不能依赖家庭主机直连微信接口

推荐方案：

- 在公网服务器上部署一个轻量 `wechat-connector`
- 所有访问微信官方 API 的请求统一经该连接器转发
- 微信公众平台的开发者 IP 白名单只配置公网服务器固定 IP

这样可以做到：

- 家庭主机继续承载主业务与算力
- 微信接口始终由固定公网 IP 出口访问
- 不需要把主业务迁移到公网服务器

## 8. 邮箱注册与登录设计

### 8.1 必须补齐的能力

建议第一阶段至少支持：

- 邮箱注册
- 邮箱验证码验证
- 邮箱密码登录
- 忘记密码
- 重置密码

### 8.2 设计原则

- 邮箱应当成为正式主凭据之一
- 邮箱唯一性要保证
- 验证成功前应限制关键敏感操作
- 密码只存哈希，不可进入支付 token 或业务参数

### 8.3 账号关系建议

建议把历史 `username` 处理为兼容字段，而不是未来唯一登录主键。

后续推荐登录方式优先级：

- 邮箱 + 密码
- 微信登录
- 历史用户名密码仅作为过渡兼容

## 9. 爱发电链路改造建议

### 9.1 当前问题

当前支付流程的问题核心在于：

- 生成支付链接时依赖 `username + password`
- `custom_id` 中存在密码语义
- 订单激活还保留旧“未注册用户支付即开户”的逻辑

这和官网、微信登录、邮箱账号体系冲突。

### 9.2 新目标

支付流程应改造为：

- 基于已登录用户发起
- 基于 `user_id` 而不是 `username/password`
- 基于 `payment_intent` 驱动
- 支付只负责发放权益，不负责定义账号身份

### 9.3 推荐支付模型

建议新增：

#### `payment_intents`

- `id`
- `user_id`
- `provider`
- `provider_trade_no`
- `plan_id`
- `action`
- `amount`
- `status`
- `created_at`
- `confirmed_at`

#### `payment_events`

- `intent_id`
- `event_type`
- `raw_payload`
- `processed_at`

#### `entitlement_grants`

- `user_id`
- `intent_id`
- `grant_type`
- `grant_payload`
- `applied_at`

### 9.4 custom_id 内容建议

新的 `custom_id` 不应再包含密码。

建议只放：

- `payment_intent_id`
- `user_id`
- `action`
- `plan_id`
- `amount`
- `ts`
- `nonce`
- `sign`

这样能做到：

- 支付凭据最小化
- 回调后可安全映射到内部订单
- 不暴露账号敏感信息

### 9.5 推荐支付流程

1. 用户登录官网
2. 选择套餐或加油包
3. 后端创建 `payment_intent`
4. 后端生成爱发电支付链接
5. 用户跳转支付
6. 爱发电回调 Webhook
7. 系统校验并查询订单
8. 根据 `payment_intent_id` 发放权益
9. 用户中心展示订单状态与生效结果

### 9.6 关于“支付即开户”

不建议继续保留“未注册用户直接支付并自动开户”的旧逻辑。

建议改为：

- 先注册/登录
- 再支付

这样：

- 微信登录用户可直接购买
- 邮箱用户可直接购买
- 账号归属不混乱
- 不需要在支付链路里处理密码与开户问题

## 10. 官网与用户中心迁移方案

### 10.1 官网建议模块

官网建议拆成以下页面：

- 首页
- 功能介绍
- 套餐定价
- 下载页
- 使用文档
- 登录页
- 注册页
- 微信登录引导页
- 用户中心首页
- 账户与绑定页
- 用量页
- 套餐与订单页

### 10.2 用户中心迁移范围

当前客户端中与用户资产相关的能力，建议全部迁移到官网：

- 账户状态
- 到期时间
- 日额度使用情况
- 加油包余额
- 套餐展示
- 爱发电付款
- 订单查询
- 账号绑定

### 10.3 前后端建议

前端可以单独做，也可以先用后端模板过渡，但从长期维护看，建议：

- 官网/用户中心前端独立
- 身份中心与业务 API 独立

推荐交互关系：

- 前端调用 `account` 域认证接口
- 前端调用 `portal/billing` 域用户中心接口
- 客户端调用 `api` 域资源接口

## 11. 公网服务器 + 家庭主机部署方案

### 11.1 当前约束

现实条件如下：

- 家庭环境部署主服务
- 家庭公网 IP 动态变化
- 需要静态公网 IP 承接微信/公众号/支付回调
- 公网服务器性能较差
- 不希望将计算服务和大型容器迁移到公网服务器

### 11.2 推荐方案

采用：

- 公网服务器作为边缘入口
- 家庭主机作为主业务与主算力节点

#### 公网服务器负责

- 静态公网 IP
- 域名解析入口
- HTTPS 证书
- Nginx/Caddy 反向代理
- FRP 服务端
- 轻量 `wechat-connector`
- 可选的静态官网页面托管
- 可选的轻量 webhook 中继

#### 家庭主机负责

- FastAPI 主业务
- OAuth2 身份中心
- 用户中心
- 爱发电业务逻辑
- 数据库
- Redis
- Whisper / SenseVoice / 翻译 / TTS 相关算力服务

### 11.3 推荐域名规划

- `www.example.com`：官网展示页
- `account.example.com`：登录、注册、OAuth2、用户中心
- `api.example.com`：客户端 API / 资源接口
- `admin.example.com`：后台管理
- `pay.example.com`：支付回调与订单入口，可选

### 11.4 推荐流量路径

1. 用户访问域名
2. DNS 解析到公网服务器
3. 公网服务器处理 TLS
4. 公网服务器反向代理到 FRP 暴露的家庭服务
5. 家庭主机完成业务处理与算力调用

### 11.5 为什么不把主业务迁到公网服务器

原因很明确：

- 公网服务器性能差
- 语音转写和翻译对算力更敏感
- 后续官网、身份中心、支付逻辑其实不重
- 真正重的是计算服务和数据库

所以最优策略不是“迁移服务”，而是“迁移入口”。

### 11.6 官网静态资源如何放置

有两种可行方案：

#### 方案 A

- 官网静态页部署在公网服务器
- 用户中心/API 反代到家庭主机

优点：

- 首屏更稳
- 公网服务器负载很低
- SEO 更友好

#### 方案 B

- 官网、用户中心、API 全部反代回家庭主机

优点：

- 部署简单
- 只维护一份应用

缺点：

- 完全依赖家庭网络链路

推荐优先使用方案 A。

- 建立统一认证中心基础能力
- 重构爱发电链路，去掉密码耦合

- 邮箱登录与旧客户端兼容都依赖新的身份模型
- 爱发电链路如果不先改，官网支付会继续受旧模型拖累

## 14. 风险点与注意事项

### 14.1 高风险点

- 旧用户迁移与新账号模型不兼容
- 微信身份与邮箱身份的合并策略不清晰
- 旧客户端仍依赖 `/api/login`
- 爱发电旧订单与新订单模型并存
- 公网入口稳定但家庭链路不稳时，用户中心和支付回调会受影响

### 14.2 必须避免的做法

- 一边做官网页面，一边继续在旧 `User + JWT + user_center` 上堆功能
- 把公众号登录直接做成另一套独立用户系统
- 把密码继续放进支付链路 token
- 为了静态 IP 把全部计算服务迁到公网服务器

### 14.3 建议补充的基础设施

后续建议逐步补齐：

- 正式数据库迁移工具
- 邮件发送服务
- 统一审计日志
- 登录与安全事件日志
- 统一配置分环境管理
- 回调失败重试机制
