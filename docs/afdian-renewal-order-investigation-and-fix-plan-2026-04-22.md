# 爱发电续费订单异常排查与修复计划

日期：2026-04-22  
范围：`81` 新后端（`voicelink-backend` / `voicelinkvr_server_test`）、门户前端 `Sponsor` 页面、爱发电支付与 webhook 激活链路  
状态：排查完成，待修复  

## 1. 背景

本轮排查围绕以下两类用户问题展开：

1. 新用户、免费用户或已过期回到免费额度的用户，本应可以自由选择付费档位续费，但实际未能创建目标金额订单。
2. 爱发电实际支付结果与本地订单快照不一致时，系统仍然完成激活，导致档位被错误写入。

本次重点样本：

- 爱发电商户单号：`20260422125529494852523845`
- 81 新后端用户：`user_uuid=17ad73dc-c957-450b-8bc3-4faa6f83796d`
- 当前用户名：`莉莉丝`

说明：

- 本文不把“53 与 81 共用同一把 `AFDIAN_CUSTOM_ID_KEY`”列入本轮修复项。该配置当前被视为运维层固定设计，不在本轮变更范围内。

## 2. 已确认事实

### 2.1 这次错单不是旧账号合并直接导致

数据库与请求日志显示，81 上这名用户的时间线如下：

- `2026-04-22 04:50:46`：新账号创建
- 注册后初始用户名为 `1511465076`
- `2026-04-22 04:51:29`：`PATCH /v2/api/account/profile` 改名为 `莉莉丝`
- `2026-04-22 04:52:07`、`04:52:09`：两次 `POST /v2/api/billing/order-intents` 返回 `400`
- `2026-04-22 04:53:17`、`04:53:19`：再次两次 `POST /v2/api/billing/order-intents` 返回 `400`
- `2026-04-22 04:55:04`：一次 `POST /v2/api/billing/order-intents` 返回 `200`
- `2026-04-22 04:56:46`、`04:57:08`：两次 `POST /v2/api/account/legacy-link` 返回 `403`

同时数据库中：

- `v2_user.legacy_user_id = NULL`
- `v2_user_identity_link` 对该 `user_uuid` 的记录数为 `0`

结论：

- 错单发生时，这个账号还没有成功完成旧账号绑定。
- “合并旧账号时就被识别成 5 元档”不符合本次样本订单的实际时间线。

### 2.2 新用户注册时并不会默认被写成 5 元档

注册逻辑见：

- [auth.py](D:/git/gitlab/VoiceLinkServer1/src/routers/auth.py)

当前实现中，新用户注册会：

- 读取 `free_plan`
- 将 `limit_rule` 初始化为免费档规则
- 然后调用 `rebuild_user_entitlement_state_from_legacy_fields`

换句话说，新用户注册时应先进入免费额度状态，而不是直接进入 `5 元档 / 3000/day`。

## 3. 问题总结

### 问题 1：系统没有允许本应可自由续费的新用户创建 10 元订单

这是本次事故的第一处核心问题。

正确业务预期：

- 新用户
- 免费用户
- 已过期回到免费额度的用户

在续费时都应该可以自由选择可售付费档位，而不应被限制在当前档位。

现有后端规则本身是这样设计的，见：

- [user_center.py](D:/git/gitlab/VoiceLinkServer1/src/routers/user_center.py)

其中：

- 新用户 / 免费 / 已过期 时，`renew_prices = all_paid_prices`

因此，规则设计并没有要求“只能 5 元续费”。

但在本次真实时间线中，用户先尝试创建更高金额订单，多次失败：

- `04:52:07` -> `400`
- `04:52:09` -> `400`
- `04:53:17` -> `400`
- `04:53:19` -> `400`

然后才在 `04:55:04` 成功创建出一张 `5 元 / 2 月 / 预期 10 元` 的订单。

因此，本次第一问题应表述为：

> 系统没有正确允许这个本应可自由续费的新用户创建 10 元订单，导致用户最终退而求其次，成功创建出一张错误的 5 元订单。

### 问题 2：订单激活只做了“下限校验”，没有做真实金额一致性校验

当前激活逻辑会读取本地订单快照或 `custom_id` 中的：

- `plan_price`
- `months`
- `requested_amount`

然后只检查：

- 实付金额是否 **不少于** 预期金额

只要 `actual_amount >= requested_amount`，就允许激活。

这导致：

- 本地订单快照：`5 元 / 2 月 / 预期 10 元`
- 爱发电实际支付：`30 元 / 3 月`

由于 `30 >= 10` 成立，系统仍然把订单按 `5 元档` 激活。

这属于明显的校验不足。

### 问题 3：失败下单原因没有清晰反馈给用户

用户在 `04:52~04:53` 之间连续四次 `order-intents` 返回 `400`，但当前排查中：

- `v2_request_audit_log.extra_payload = NULL`
- 应用日志没有记录失败详情
- 用户端没有足够明确的错误提示可供回看

因此用户只能主观感知为：

- “10 元不行”
- “按钮点不了 / 下单失败”

这会直接推动用户去尝试其他金额，放大事故概率。

### 问题 4：请求审计能力不足，无法还原前端真实下单请求体

当前 `order-intents` 的请求体没有被记录到审计日志中。

所以现在虽然我们已经能确定：

- 成功的那次请求最终建成了 `5 元 / 2 月`

但我们还不能直接从日志中看到浏览器当时提交的：

- `action`
- `months`
- `targetMonthlyPrice`
- `guideToken`

这使根因定位仍然缺少最后一层直接证据。

### 问题 5：支付页与本地订单快照之间缺少强一致性约束

当前系统允许出现下面这种情况：

- 本地订单快照：`5 元 / 2 月`
- 爱发电实际支付结果：`30 元 / 3 月`

但激活阶段并不会把这种不一致拦下。

这意味着：

- 用户可以在支付侧改金额或月份
- 系统仍然按旧快照执行激活

这是支付链路设计上的风险点。

## 4. 目前最合理的根因判断

按当前证据，最稳的判断是：

1. 这次错单与旧账号绑定无直接关系
2. 用户在 81 上是新注册账号
3. 她在成功下单前，多次尝试创建目标订单失败
4. 最终成功的请求，在进入后端时就已经是 `5 元 / 2 月`
5. 后续用户在爱发电侧支付成了 `30 元 / 3 月`
6. 激活逻辑又没有做强一致性校验，最终把错误订单正式写入订阅状态

当前仍未完全坐实的一点：

- 为什么前四次 `400`
- 为什么最终成功的这次请求会变成 `5 元 / 2 月`

其中最值得优先怀疑的两条路径是：

- 改名后旧 `guideToken` 失效，导致前两次 `400`
- 前端 `Sponsor` 状态机在多次失败后没有正确重置 `action/months/amount`，最终把错误参数提交给了后端

## 5. 修复计划

### P0：阻止错误激活继续发生

1. 在激活阶段增加“真实支付结果一致性校验”
   - 校验本地订单快照与爱发电返回结果是否一致
   - 至少覆盖：
     - 预期金额 vs 实付金额
     - 月份 vs 爱发电返回月份
     - 目标档位 / 目标月价
   - 当出现不一致时：
     - 不激活
     - 记录 `activation_error`
     - 将订单保留为异常状态供人工处理

2. 补充用户可见错误提示
   - 下单失败时前端必须明确显示失败原因
   - 激活失败时用户侧必须能看到“订单金额或月份与系统订单不一致”这类明确提示

### P0：修复“本应允许 10 元续费却无法创建”的问题

3. 排查并修复新用户 / 免费用户 / 过期用户的 `order-intents` 失败原因
   - 重点确认前四次 `400` 的真实失败 detail
   - 需要把 `order-intents` 的失败 detail 输出到日志或审计表
   - 若确认为 `guideToken username mismatch`，则在改用户名后主动刷新或失效旧 token
   - 若确认为前端提交参数错乱，则修复前端状态机

4. 前端 `Sponsor` 页面增加更严格的状态同步与错误反馈
   - 变更用户名、刷新 guide 后，重新同步：
     - `selectedAction`
     - `selectedMonths`
     - `selectedAmount`
   - 当后端返回 `400` 时，把 detail 明确展示给用户
   - 如果当前 action 下金额不合法，不应只是灰按钮，还应展示原因

### P1：提升可排查性

5. 为 `/v2/api/billing/order-intents` 增加请求参数审计
   - 记录精简后的安全字段到审计日志：
     - `action`
     - `months`
     - `targetMonthlyPrice`
     - `addonAmount`
     - `guideToken` 中的摘要信息（不要记明文敏感 token）
   - 同时记录失败 detail

6. 为支付与激活链路增加结构化日志
   - 本地建单日志
   - 跳转支付日志
   - webhook 直达激活日志
   - 异常激活拒绝日志

### P1：补齐回归验证

7. 新增端到端场景验证
   - 新用户直接创建 `10 元续费`
   - 免费用户直接创建 `10 元续费`
   - 已过期用户直接创建 `10 元续费`
   - 改名后重新下单
   - 爱发电侧金额被修改时应拒绝激活

8. 增加异常订单人工处理预案
   - 当前已错误落库的订单如何回滚
   - 用户如何恢复到正确档位
   - 待支付错单如何作废

## 6. 建议的修复顺序

建议按下面顺序推进：

1. `P0`：激活一致性校验
2. `P0`：明确 `order-intents` 失败原因
3. `P0`：修复新用户/免费用户无法创建目标档位订单的问题
4. `P1`：补齐请求审计与结构化日志
5. `P1`：补齐回归测试

## 7. 当前运维建议

在代码修复前，建议：

1. 不要让用户继续尝试修改支付页金额/月份后付款
2. 对已出现错档位的账号先人工校正订阅状态
3. 对异常 pending 单保留记录，不要继续复用

## 8. 最终结论

本次事故的正确主线应归纳为：

1. 用户是 81 上的新用户，不是旧账号合并直接导致
2. 她本应可以创建 10 元续费订单
3. 系统却没有允许她创建目标金额订单
4. 用户随后成功创建了一张错误的 5 元订单
5. 用户在爱发电侧实际支付结果又与本地订单快照不一致
6. 激活阶段因为缺少强一致性校验，最终把用户正式写成了 5 元档

因此，本轮最重要的两个问题是：

- 没有正确允许本应可自由续费的用户创建 10 元订单
- 激活阶段没有做真实金额/月份/档位一致性校验
